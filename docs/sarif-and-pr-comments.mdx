# SARIF and PR Comments

## Why This Matters

Developers should not search long CI logs to understand a security failure.

## Actual Security Problem

Security tools generate output, but the feedback is not visible where developers review code.

In real implementation, the issue is not only the tool. The main issue is where the check runs, what permission it gets, and whether the result blocks risky code.

## How Attackers Misuse It

This is not an attacker technique directly, but poor feedback delays fixes and lets risky code move forward.

They do not always need a zero-day. Many times they use normal engineering paths like pull requests, package updates, workflow changes, or leaked credentials.

## Common Wrong Setup

Teams upload artifacts only and expect developers to download JSON reports.

```yaml
name: unsafe-sarif-pr-feedback
on:
  pull_request:
permissions: write-all
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@master
      - run: echo "$CLOUD_SECRET"
```

What is wrong here:

- write-all gives more access than required.
- checkout@master is not a stable pinned version.
- Secret handling is careless.
- There is no clear PR output or quality gate.

## Practical Implementation

```yaml
name: sarif-pr-feedback
on:
  pull_request:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
  security-events: write
  pull-requests: write
jobs:
  security-check:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Run SARIF upload and PR comments
        run: |
          echo "Run SARIF upload and PR comments here"
          echo "Fail only on agreed severity threshold"
```

## Useful Commands

```bash
cat results.sarif | jq ".runs[0].results[0]"
gh pr comment 12 --body-file summary.md
```

## Example Result

```text
GitHub Code Scanning annotation added on changed line.
```

## Secure Fix

Upload SARIF for code findings and add a short PR summary with counts and next steps.

Also make sure the check is required in GitHub rulesets or branch protection. Otherwise it only reports and does not stop risky code.

## Practical Recommendations

- Start with high-confidence checks.
- Keep permissions minimum.
- Put security feedback in the pull request.
- Make only important checks blocking in the beginning.
- Tune false positives before strict enforcement.
- Track exceptions with owner, reason, and expiry.
