# SCM Security

## Why This Matters

SCM is where product code, history, workflows, and review decisions live.

## Actual Security Problem

If repository permissions, branches, and pull requests are weak, attackers can change code before the pipeline even starts.

In real implementation, the issue is not only the tool. The main issue is where the check runs, what permission it gets, and whether the result blocks risky code.

## How Attackers Misuse It

Attackers target stale users, weak branch rules, leaked deploy keys, unreviewed workflow changes, and malicious pull requests.

They do not always need a zero-day. Many times they use normal engineering paths like pull requests, package updates, workflow changes, or leaked credentials.

## Common Wrong Setup

One common issue is allowing direct pushes to main because the team trusts everyone. This breaks audit and review flow.

```yaml
name: unsafe-scm-security-check
on:
  pull_request:
permissions: write-all
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@master
      - run: echo "$CLOUD_SECRET"
```

What is wrong here:

- write-all gives more access than required.
- checkout@master is not a stable pinned version.
- Secret handling is careless.
- There is no clear PR output or quality gate.

## Practical Implementation

```yaml
name: scm-security-check
on:
  pull_request:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
  security-events: write
  pull-requests: write
jobs:
  security-check:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Run repository policy checks
        run: |
          echo "Run repository policy checks here"
          echo "Fail only on agreed severity threshold"
```

## Example Result

```text
Ruleset blocked merge: required check pr-security is missing.
```

## Secure Fix

Protect main, require pull requests, use CODEOWNERS, review workflow changes carefully, and remove stale access.

Also make sure the check is required in GitHub rulesets or branch protection. Otherwise it only reports and does not stop risky code.

## Practical Recommendations

- Start with high-confidence checks.
- Keep permissions minimum.
- Put security feedback in the pull request.
- Make only important checks blocking in the beginning.
- Tune false positives before strict enforcement.
- Track exceptions with owner, reason, and expiry.
